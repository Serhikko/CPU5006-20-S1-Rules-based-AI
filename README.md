# Car Evaluation: a rule-based expert system (CPU5006 S1)

A small expert system that decides how acceptable a car is (`unacc`, `acc`, `good`, `vgood`)
from six attributes, explains every decision, and is evaluated honestly against a baseline
and the five-rule class example from Session 3. Built for the CPU5006 Artificial Intelligence module (Bath Spa
University), Assessment S1, November 2026.

## The problem and the data

The Car Evaluation data set (Bohanec, 1997) describes 1,728 cars with six categorical
attributes:

| attribute | values (low to high) | meaning |
|---|---|---|
| buying | low, med, high, vhigh | buying price |
| maint | low, med, high, vhigh | price of maintenance |
| doors | 2, 3, 4, 5more | number of doors |
| persons | 2, 4, more | how many people it carries |
| lug_boot | small, med, big | size of the luggage boot |
| safety | low, med, high | estimated safety |

Every combination of values appears exactly once (4 x 4 x 4 x 3 x 3 x 3 = 1,728). There are no
missing values and no duplicates. The classes are very unbalanced: unacc 1,210 (70.0%), acc 384
(22.2%), good 69 (4.0%), vgood 65 (3.8%), so always answering `unacc` is already 70% accurate.
That is the baseline every model has to beat.

The labels were generated by a hand-built expert decision model (Bohanec and Rajkovič, 1988) made with
the DEX shell (Bohanec and Rajkovič, 1990), with hidden middle concepts PRICE, COMFORT and TECH. The data is
therefore synthetic:
it tells us how well rules can recover an expert's rules, not how real buyers behave.

## How to run

Python 3.12 or newer and pandas. From the project folder:

```
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe explore.py                       # data exploration and the split check
.\.venv\Scripts\python.exe evaluate.py                      # TRAIN accuracy, confusion matrix, recall, error analysis
.\.venv\Scripts\python.exe evaluate.py test                 # the same plus the held-out TEST score
.\.venv\Scripts\python.exe explain.py low low 4 4 big high  # explain one car (buying maint doors persons lug_boot safety)
.\.venv\Scripts\python.exe backward.py                      # backward-chaining proofs for two example cars
.\.venv\Scripts\python.exe class_example.py                 # the five-rule class example, scored on the same split
.\.venv\Scripts\python.exe -m unittest discover -s tests -t .
```

(On Linux or macOS use `.venv/bin/python` instead.) The notebook `S1_walkthrough.ipynb` runs the same
steps in order with explanations (the crosstabs and the explanation are repeated inline; the unit tests run from the
command line); open it in VS Code or Jupyter and choose "Run All" (running it needs
`pip install jupyter` in the same environment; the saved outputs can be read without that).

## How the system reasons

1. **Facts.** A car becomes six facts such as `safety=high` (`row_to_facts`).
2. **Rules.** Each rule is a set of conditions, a conclusion and a one-sentence reason. All
   conditions must be facts (AND); OR is written as two rules. Conclusions that start with `car=`
   are final answers; the others are helper concepts (`cheap_to_buy`, `price=low`, `family_car`,
   `roomy`, ...) that other rules can use, so rules build on rules. The concepts mirror the hidden
   PRICE and COMFORT concepts of the original model.
3. **Forward chaining.** `forward_chain` applies the rules again and again until a full pass adds
   no new fact. Each rule fires at most once. Every fired rule is recorded, and that record is the
   explanation.
4. **Conflict resolution.** Several final answers can be proved for one car. The verdict is decided
   by priority: a veto (`car=unacc`) always wins; otherwise the best proved class (vgood, then good,
   then acc); if nothing was proved, the default is `unacc`, the majority class. This differs from
   the "first match wins" strategy used in the module's class example.
5. **Backward chaining.** `prove(goal, facts, rules)` starts from a question such as `car=vgood`,
   finds a rule that concludes it, and tries to prove each condition in the same way down to known
   facts, printing one line per step.

Example (`explain.py low low 4 4 big high`): the cheap-price rules fire first and prove
`price=low`; `persons=4` proves `family_car`; then `car=acc`, `car=good` and `car=vgood` are all
concluded, and the verdict is `vgood`. For `low low 4 2 big high` the two-seater veto fires and the
verdict is `unacc` whatever else is proved.

## Evaluation protocol

- Stratified 70/30 hold-out split with a fixed seed: train 1,209 rows, test 519. Stratified because
  `good` and `vgood` are only 4% each and the file is sorted by attribute.
- The exploration crosstabs (`explore.py`) were run on the whole file before the split; the two
  vetoes they revealed (persons=2, safety=low) and the three buying x maint combinations that Claude Code
  pointed me to (the price=vhigh veto) are identical on the training half. From v1 on, the rules were improved on
  the training half only: after each version the training errors were analysed (`evaluate.py` prints
  what the wrong predictions have in common), rules were added or changed, and the test score was
  recorded once per version with `evaluate.py test`. The test half was never used to choose rules.
- Reported: accuracy, confusion matrix and recall per class, because accuracy alone hides the two
  small classes.
- Comparisons: the majority baseline and the five-rule class example from Session 3.

## Results

| version | rules | train accuracy | test accuracy | what changed |
|---|---|---|---|---|
| baseline (always unacc) | 0 | 0.701 | 0.699 | |
| Session 3 class example (first match) | 5 | 0.731 | 0.728 | |
| v1 | 19 | 0.892 | 0.882 | vetoes, price and family concepts, acc/good/vgood rules |
| v2 | 30 | 0.937 | 0.915 | a price grid (low, med, high, vhigh) instead of one price=low concept; a roomy concept; good at medium safety needs a boot of at least med; vgood also at price=med |
| v3 | 33 | 0.963 | 0.948 | grid completed for a very high buying price (vhigh+low, vhigh+med -> price=high); a high price with a small boot and medium safety is unacceptable |

Final version (v3) on the test half, 519 rows (`evaluate.py test`):

| real \ predicted | unacc | acc | good | vgood |
|---|---|---|---|---|
| unacc | 340 | 21 | 2 | 0 |
| acc | 0 | 113 | 2 | 0 |
| good | 0 | 0 | 21 | 0 |
| vgood | 0 | 1 | 1 | 18 |

Recall per class: unacc 0.94, acc 0.98, good 1.00, vgood 0.90. 23 of the 27 test errors are real `unacc`
cars that the rules let through as `acc` or `good`; no acceptable car is ever rejected.

No single attribute can beat the baseline on this data. In the exploration crosstabs the most common
class of every value of every attribute is `unacc`, so even OneR (Holte, 1993), the simplest rule
learner, which predicts the most common class for each value of one attribute, would answer `unacc`
for every car and score 0.70. The classes depend on combinations of attributes, which is exactly what
the chained concept rules provide.

## What it still gets wrong and other limitations

- A car with a very high buying price, a medium boot and medium safety (for example
  `vhigh med 2 4 med med`, price=high in my grid) is `unacc` in the data but the model says `acc`: the hidden
  COMFORT and TECH concepts are only approximated. Of the 34 training `unacc` cars that v3 still calls `acc`, 23 have
  two doors and 19 a medium boot; a "cramped" concept (two doors with a small or medium boot) would be the next version.
- `cheap_to_buy` is a leftover from v1: two rules still conclude it, but since the v2 price grid no rule uses it.
  It is harmless (it only adds one line to an explanation) and would go in the next version.
- The knowledge base only knows the six attributes and their fixed words. A car described in
  pounds, years or brands first has to be mapped onto these six words.
- Every improvement came from error analysis by hand. The rule base grew from 19 to
  33 rules, and a change to one concept changes the behaviour of every rule that uses it.
- The data is synthetic (generated from an expert's rules), which is why hand-written rules can
  score so high. Real buyers disagree with each other, and real data would be noisier.
- One hold-out split instead of cross-validation: the test numbers depend a little on the seed.
